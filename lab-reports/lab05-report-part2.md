## 1. Мета роботи
Поглибити практичні навички розробки REST API на базі мікрофреймворку Flask, спроєктувати та реалізувати бізнес-логіку підсистеми управління замовленнями (Orders), промокодами (Coupons) та клієнтською базою (Customers). Забезпечити дотримання архітектурного стилю REST, коректно використовувати методи протоколу HTTP (`GET`, `POST`, `PATCH`, `DELETE`) та відповідні коди стану (`200 OK`, `201 Created`, `204 No Content`, `400 Bad Request`, `404 Not Found`). Реалізувати сувору багаторівневу валідацію вхідних даних, автоматично згенерувати інтерактивну специфікацію OpenAPI/Swagger за допомогою Flasgger, розробити версію API v2 для аналітики та пагінації замовлень, а також провести комплексне тестування через `unittest` та Postman/Bruno.

## 2. Особистий внесок у командну роботу (Частина 2 — 50%)

У рамках розподілу завдань у команді з двох осіб (Биков Олександр — Частина 1, Мазурик Матвій — Частина 2) мною виконано другу половину проєкту:

1. **Підсистема керування замовленнями (Orders API — `routes/api_v1.py`):**
   - `GET /api/v1/orders` — вибірка списку замовлень з можливістю динамічної фільтрації за поточним статусом (`?status=`) або пошуком за номером телефону клієнта (`?phone=`).
   - `GET /api/v1/orders/<int:order_id>` — отримання повних відомостей про замовлення разом із пов'язаними купленими позиціями (`order_items`) та даними товару (назва, категорія, ціна) на основі зв'язку Many-to-Many у СКБД SQLite. У разі відсутності повертається статус `404 Not Found`.
   - `POST /api/v1/orders` — оформлення замовлення з автоматичним розрахунком знижки за промокодом, збереженням у транзакції записів замовлення та позицій `order_items`, прив'язкою до існуючого клієнта та поверненням створеного об'єкта зі статусом `201 Created`.
   - `PATCH /api/v1/orders/<int:order_id>/status` — часткове оновлення статусу життєвого циклу замовлення («Нове», «В обробці», «Відправлено», «Доставлено», «Скасовано») з поверненням коду `200 OK`.
   - `DELETE /api/v1/orders/<int:order_id>` — видалення замовлення із системи з каскадним видаленням пов'язаних позицій (`ON DELETE CASCADE`) та поверненням коду `204 No Content`.

2. **Підсистема промокодів та клієнтів (Coupons & Customers API — `routes/api_v1.py`):**
   - `GET /api/v1/coupons` — отримання актуального переліку діючих промокодів магазину та встановленого для них відсотка знижки.
   - `POST /api/v1/coupons/validate` — сервіс швидкої валідації введеного клієнтом промокоду (перевірка існування коду незалежно від регістру символів, повернення відсотка знижки або `valid: false`).
   - `GET /api/v1/customers` — отримання списку зареєстрованих клієнтів магазину з контактними даними.

3. **Рівень 2 (Інтерактивна документація Flasgger / Swagger UI):**
   - Для кожного нового маршруту створено докладний YAML-опис у форматі docstring згідно зі специфікацією OpenAPI 2.0.
   - Задокументовано параметри шляху (`path`), параметри запиту (`query`), схеми JSON-тіла (`body`), моделі відповідей зі статусами `200`, `201`, `204`, `400`, `404` та реалістичними прикладами (`example`).
   - Ендпоінти логічно згруповано за відповідними тегами: `Orders (Частина 2 - Замовлення)`, `Coupons (Частина 2 - Промокоди)`, `Customers (Частина 2 - Клієнти)`, `Orders (API v2 - Рівень 3)`. Інтерактивне тестування доступне за адресою `http://127.0.0.1:5000/apidocs/`.

4. **Рівень 3 (Валідація вхідних даних та версіонування):**
   - **Валідація даних:**
     - Перевірка обов'язковості та структури JSON-тіла запитів.
     - Перевірка довжини рядків: ім'я покупця (`len >= 2`), контактний телефон (`len >= 7`), адреса доставки (`len >= 5`).
     - Глибока валідація масиву `items`: перевірка наявності хоча б одного товару, цілочисельності `product_id`, додатного значення кількості (`quantity > 0`) та ціни (`price > 0`).
     - Перевірка допустимості переданого статусу замовлення згідно з визначеним переліком дозволених значень (`['Нове', 'В обробці', 'Відправлено', 'Доставлено', 'Скасовано']`).
     - У разі виявлення помилок формується відповідь `400 Bad Request` із масивом конкретних повідомлень `details`.
   - **Версіонування (API v2 — `routes/api_v2.py`):**
     - `GET /api/v2/orders/stats` — ендпоінт бізнес-аналітики, що обчислює сумарну кількість замовлень, загальний виторг магазину (`total_revenue`), середній чек замовлення (`average_order_value`) та групування кількості замовлень за їхніми статусами (`by_status`).
     - `GET /api/v2/orders` — отримання замовлень у стандартизованому інформаційному конверті (envelope) з підтримкою посторінкової пагінації (`page`, `per_page`, `total_items`, `total_pages`, `has_next`, `has_prev`), фільтрації за статусом та сортування (`newest`, `oldest`, `total_asc`, `total_desc`).

5. **Тестування:**
   - Розширено файл `postman_collection.json` двома новими категоріями запитів: `5. Замовлення (Orders v1 & v2)` (10 запитів) та `6. Промокоди та Клієнти (Coupons & Customers)` (5 запитів) з тестовими скриптами `pm.test` для перевірки кодів статусу, схем та полів відповідей.
   - Розширено набір автоматизованих тестів `test_api.py` новими сценаріями (`test_13` – `test_23`), довівши загальну кількість тестів до 23 (успішне проходження 23/23 тестів за ~0.11 с).

### 4.3. Приклад валідації помилок при оформленні замовлення (POST — 400 Bad Request)
* **Запит:** `POST /api/v1/orders`
* **Тіло запиту:**
```json
{
  "name": "",
  "phone": "123",
  "address": "",
  "items": []
}
```
* **Код відповіді:** `400 Bad Request`
* **Тіло відповіді:**
```json
{
  "error": "Помилка валідації замовлення",
  "details": [
    "Поле \"name\" має містити щонайменше 2 символи.",
    "Поле \"phone\" обов'язкове (мінімум 7 символів).",
    "Поле \"address\" обов'язкове (мінімум 5 символів).",
    "Список \"items\" має містити хоча б один товар."
  ],
  "status": 400
}
```

### 4.4. Оновлення статусу замовлення (PATCH — 200 OK)
* **Запит:** `PATCH /api/v1/orders/1/status`
* **Тіло запиту:**
```json
{
  "status": "Відправлено"
}
```
* **Код відповіді:** `200 OK`
* **Тіло відповіді:**
```json
{
  "id": 1,
  "message": "Статус оновлено",
  "status": "Відправлено"
}
```

* **Сценарій помилки при некоректному статусі:**
* **Запит:** `PATCH /api/v1/orders/1/status` з тілом `{"status": "Невідомий"}`
* **Код відповіді:** `400 Bad Request`
* **Тіло відповіді:**
```json
{
  "error": "Некоректний статус. Дозволені: ['Нове', 'В обробці', 'Відправлено', 'Доставлено', 'Скасовано']",
  "status": 400
}
```

### 4.5. Перевірка валідності промокоду (POST — 200 OK)
* **Запит на перевірку дійсного коду:** `POST /api/v1/coupons/validate`
* **Тіло запиту:** `{"code": "SALE10"}`
* **Тіло відповіді (200 OK):**
```json
{
  "code": "SALE10",
  "discount_percent": 10,

}
```

* **Запит на перевірку недійсного коду:** `POST /api/v1/coupons/validate`
* **Тіло запиту:** `{"code": "UNKNOWN_PROMO"}`
* **Тіло відповіді (200 OK):**
```json
{
  "message": "Промокод недійсний або не існує",
  "valid": false
}
```
